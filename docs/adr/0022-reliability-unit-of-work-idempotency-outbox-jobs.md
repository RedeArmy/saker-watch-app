# ADR-0022: Reliability machinery — unit of work, idempotency, outbox/inbox and job queue

- **Status:** accepted
- **Date:** 2026-10-13
- **Deciders:** Eder

## Context
Milestone 1.3 implements the mechanisms promised by ADR-0005 and ADR-0017. The open question is how a use case that touches several module contexts, the idempotency row and the outbox can be exactly-once without distributed transactions, given one PostgreSQL database and one DbContext per module.

## Decision
**1.3a Unit of work.** Every request scope owns one `DbSession`: a single `NpgsqlConnection` that all module DbContexts of the scope use. Commands (`ICommand`, `ICommand<T>`, marked `ITransactionalRequest`) run through `UnitOfWorkBehavior`, placed after validation: it begins a transaction on the session, commits on a success result and rolls back on a failure result or an exception. A save interceptor makes each context join that transaction (`UseTransaction`), so writes of several modules, the idempotency row and the outbox commit or roll back together. Calls nest (only the outermost commits; a nested rollback forbids the outer commit). Outside a unit of work EF behaves normally and the user-context interceptor tags each connection open. Queries never open a transaction. Hosts without a database get a no-op unit of work.

**1.3b Idempotency (Postgres-only operations).** The `Idempotency-Key` behavior runs inside the unit of work: it inserts `platform.idempotency_keys` with `ON CONFLICT DO NOTHING` in the same transaction as the effect. A concurrent duplicate blocks on the unique index until the first transaction ends, then reads the committed row and replays it, or proceeds if the first one rolled back; a lock timeout maps to 409 with `Retry-After`. A crash before commit leaves no row and no effect, so a retry executes once. Same key with a different request hash gives 422. Only success results are stored; failure results roll back and the key is not kept, so a retry re-evaluates (deterministic errors repeat). The explicit `in_progress` lease and takeover of ADR-0017 are reserved for cross-store operations (Mongo plus Postgres, Phase 4), where the effect cannot share one transaction; they are introduced with the first such feature. Oversized responses (> 64 KB) are not snapshotted and a replay returns a conflict pointing to a GET.

**1.3c Outbox and inbox.** Handlers add integration events to an outbox writer; the unit of work persists them in the same transaction. The Worker's dispatcher claims pending rows with `FOR UPDATE SKIP LOCKED`, publishes, and marks them processed, with attempts and exponential backoff with jitter. Consumers record `(consumer, message_id)` in `platform.inbox_messages` in the same transaction as their effect. Concretely: handlers call `IOutbox.AddAsync` inside the unit of work, which inserts the row with trace, correlation and user ids and the event id as primary key; events carry a stable `[IntegrationEventName]` (never the CLR type name) and only ids and non-personal data, never email or names. The dispatcher processes one message per unit of work: it claims the row, runs every `IIntegrationEventConsumer<T>` (each guarded by an inbox row named after the consumer type), marks the row processed and commits, so the consumers' effects, their inbox marks and the processed mark are atomic and a failing consumer rolls back all of them. Failures are recorded on a separate connection (attempt count, backoff with jitter, short error text without stack); after `MaxAttempts` the row is parked and no longer claimed. Delivery is at least once and not ordered. Renaming a consumer class changes its inbox name, so a rename redelivers; keep consumer names stable.

**1.3d Job queue.** Jobs are enqueued through `IJobEnqueuer`, which calls `platform.enqueue_job` (deterministic `job_key`, `ON CONFLICT DO NOTHING`; the API role has no table access) and joins the caller's unit of work, so a job exists only if the change that needed it committed. A payload carries a stable `[JobType]` name. The Worker claims with `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED)`, which takes either a due pending job or one whose lease has expired, and stamps a fresh lease token and expiry. While the handler runs the worker renews the lease every third of its duration; if the renewal finds the token gone it cancels the handler. The handler runs in a unit of work together with the completion `UPDATE ... WHERE lease_token = @token AND state = 'leased'`: when another worker has taken over, zero rows match, the attempt throws `LeaseLostException` and its effects roll back (fencing). Failures roll back, then record the attempt on a separate connection (backoff with jitter, short error text) and the job returns to `pending`, or becomes `dead` once `attempts >= max_attempts`. A job whose last allowed attempt crashed the worker is parked as dead when its lease expires instead of looping. On shutdown the running attempt is rolled back, the lease released and the attempt not counted. Several loops per worker (`Jobs:MaxConcurrency`) share one processor; queue depth, oldest due age, in-flight and dead counts are sampled as gauges. Handlers must be re-runnable: the unit of work makes PostgreSQL effects happen once, while effects in other stores rely on idempotent writes.

## Consequences
One shared connection per scope means a scope handles one operation at a time, which holds for HTTP requests and job executions. Long transactions are bounded by the login's `statement_timeout` and `idle_in_transaction_session_timeout`. The cross-store lease path stays unimplemented until it has a real consumer, which avoids carrying untested code.
