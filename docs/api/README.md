# API guidelines

- **Purpose:** conventions every endpoint must follow; the OpenAPI contract is generated from code (ADR-0014).
- **Owner:** Eder · **Status:** approved · **Target phase:** 1 (kept current through Phase 2)

## Contract
- OpenAPI 3.x per major version; committed at `docs/api/openapi.v1.json`; CI fails on unreviewed diffs and on breaking changes.
- Swagger UI per version (dev; protected or disabled elsewhere).

## Every endpoint must declare
`WithName`, `WithSummary`, `WithDescription`, `WithTags`, typed `Produces<T>` for every status code, `ProducesProblem` (RFC 9457) for errors, auth requirement, request/response examples, and `Idempotency-Key`/pagination/ETag behavior where relevant.

## Contract workflow (implemented, milestone 1.5a)
- The document is generated from code by `Asp.Versioning.OpenApi` + `Microsoft.AspNetCore.OpenApi` and served at `/openapi/v1.json`. It declares the `bearer` scheme and a `security` requirement on every operation that is not anonymous; it pins no `servers` entry.
- `tests/Contract.Tests` hosts `Host.Api` in memory and fails when the generated document differs from `docs/api/openapi.v1.json`. After an intentional API change run `UPDATE_OPENAPI=1 dotnet test tests/Contract.Tests`, review the diff and commit it with the change.
- The same project enforces the conventions below on every mapped endpoint: versioned route, `WithName`, `WithSummary`, `WithDescription`, `WithTags`, a documented success response, 401, 500 and 503 as problems (any endpoint can answer 500 or 503), and no anonymous API endpoint.
- Exposure: the document is anonymous only in Development or with `OpenApi:Anonymous=true`; elsewhere it needs a valid token. Swagger UI (`/swagger`) is served in Development only.

## HTTP hardening (milestone 1.5c)
- **Headers on every response**, errors included: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `Cross-Origin-Resource-Policy: same-site`, `Permissions-Policy`, and `Cache-Control: no-store` unless the endpoint sets its own. Only the Swagger UI (Development) is exempt from the CSP. No `Server` header.
- **HSTS** (`max-age=31536000; includeSubDomains`, no preload) is sent over HTTPS outside Development. TLS ends at Caddy, so the API does not redirect to HTTPS itself.
- **Forwarded headers** (`X-Forwarded-For/Proto/Host`) are believed only from the proxies in `ForwardedHeaders:KnownProxies` / `ForwardedHeaders:KnownNetworks` (loopback when unset), one hop deep. Set them to the proxy's address or network in every deployment, otherwise the per-IP limit sees the proxy for everyone.
- **CORS is closed.** The Next.js BFF calls the API server to server, so no browser origin needs access. `Cors:AllowedOrigins` may list exact origins (https; http only for localhost) for a deliberate exception; no wildcard, path or credentials. Malformed security configuration stops the startup.
- **Request bodies** above 1 MiB get 413.

## Versioning
URL segment `/v1`. Additive changes are non-breaking; anything else needs `/v2`. Deprecation: `deprecated: true`, `Deprecation` and `Sunset` headers, at least one release cycle of overlap.

## Naming and shape
Plural kebab-case resources (computations are named as actions, e.g. `/v1/calculations/partial-purchase`), `camelCase` JSON, ISO-8601 UTC timestamps, **decimals always as JSON strings** (so generated clients never use floating point), stable error codes in ProblemDetails `type`. All JSON fields are camelCase, including the calculator and staleness fields.

## Errors
304 not modified (ETag), 400 validation, 401/403 auth, 404 not found, 409 conflict/concurrent duplicate, 412 `If-Match` mismatch, 422 idempotency-key payload mismatch, 428 `If-Match` required, 429 rate limit, 500 unexpected error on our side (the problem has `correlationId` and `traceId`, never the cause), 503 busy or a dependency unavailable (always with `Retry-After`; type `urn:sakerwatch:error:busy` when the database refused to wait: a lock timeout, a deadlock or a serialization failure, in which case nothing was committed and the request can be sent again), other 5xx never leak internals; every error carries a correlation id. A replayed idempotent response carries `Idempotent-Replayed: true`. Pure computations such as the calculator are exempt from `Idempotency-Key`.

The codes, what each means and what a screen does with it are in [errors.md](errors.md); `ErrorCatalogueTests` keeps that page and the source in step.

## Pipeline order (Host.Api)
`UseSakerWeb()` first: forwarded headers, HSTS (outside Development), security headers, correlation id, idempotent-replay header, exception handler, status-code pages. Then request logging, `UseRouting`, CORS, `UseSakerPreAuthenticationRateLimiting()`, Swagger UI (Development only), authentication, user resolution, authorization (default-deny), `UseSakerRateLimiting()` and the endpoints. Two limiters run: the first, before authentication, partitions by client IP (`RateLimiting:PreAuthenticationPermitLimit`, default 600 per window) and is charged only for requests that end in 401, so a flood of missing or invalid tokens is stopped before any signature is validated while accepted requests never use it up (all users behind the BFF share one address until `ForwardedHeaders` is set; ADR-0046); the second follows authentication and partitions by user id (`PermitLimit`, `ExpensivePermitLimit`). Both are sliding windows (the permits of the current window plus those of the one before it, weighted by how much of it still overlaps, must leave room: sending the limit at the end of one window and again at the start of the next does not double it). They count in the memory of the API process, which is right for the single instance deployed; with more than one API process (`Deployment:ApiReplicas`, or more seen in Redis, or `RateLimiting:Backend=Redis`) they count in Redis, so a caller has one allowance whichever process answers, and if Redis cannot be reached each process counts on its own (`sakerwatch_http_rate_limiter_fallback_total`, ADR-0048). The client IP is the real client address only for proxies listed in `ForwardedHeaders`. Both follow routing so `DisableRateLimiting` (health endpoints) and per-endpoint policies apply. CORS comes before authentication so a preflight is answered without a token.
Problem responses use `type = urn:sakerwatch:error:<code>` plus `code` (on every problem, also the ones written by the limiter, the busy database, the exception handler and the framework), `correlationId`, `traceId` and, for validation, `errors` (an object keyed by the field name as the JSON body spells it, camelCase and dotted for nested fields, for example `locale` or `identity.displayName`); unexpected failures never include their message.

## Reference endpoints (milestone 1.5)
- `GET /v1/me`: the caller's profile; creates the account on first sight.
- `PUT /v1/me/preferences`: sets the UI locale (`es-GT` or `en-US`); the worked example of a mutating endpoint. It calls `.RequireIdempotencyKey()`, which adds the required `Idempotency-Key` header to the OpenAPI operation. `Contract.Tests` fail for any mutating endpoint that neither calls `RequireIdempotencyKey()` nor `ExemptFromIdempotencyKey(reason)` and for one that does not document 400, 409 and 422.

## Stocks and the watchlist (milestone 2.6, ADR-0031 to ADR-0033)
- `GET /v1/stocks/search?q=`: finds stocks in the enabled markets (exact ticker first); limited per user and by a shared search budget (`429` with `Retry-After`; `503` with `Retry-After` when the provider cannot answer).
- `PUT /v1/watchlist/items/{market}/{ticker}`: adds the stock (`201`) or replaces the notes and target of the item (`200`); a PUT is idempotent by nature and takes no `Idempotency-Key`. It shares the stricter per-user limit of the stock search (10 a minute by default, `429` with `Retry-After`), because a new stock can spend a provider search, and a user can put at most 20 new stocks a day in the shared catalog (`429` with the code `marketdata.stock.registration_limit` and `Retry-After` until the next UTC day; a stock already in the catalog is not counted); `409` with `marketdata.stock.provider_listing_taken` when the provider's listing is already the alias of another stock. `DELETE` on the same route answers `204` whether or not the stock was there.
- `GET /v1/watchlist?sort=&order=&market=&assetType=&q=&priceStatus=&limit=&offset=`: the list with price, `priceStatus` (`current`, `stale` with `staleSince`, `pending`, `unavailable`, `delisted` with `delistedAt`) and the eight performance windows; carries an `ETag` and answers `304` to a matching `If-None-Match`. A window without a number has a `reason` instead.

## Portfolios (milestone 2.6d, ADR-0026 and ADR-0034)
- `POST /v1/portfolios` (needs an `Idempotency-Key`; `201` with a `Location`), `GET /v1/portfolios`, `GET /v1/portfolios/{id}` (both with an ETag), `PUT /v1/portfolios/{id}` (name and description), `PUT /v1/portfolios/order` (`{"portfolioIds": [...]}`, every portfolio once).
- `PUT /v1/portfolios/{id}/items/{market}/{ticker}` puts a stock of the watchlist in the portfolio (`201` added, `200` already there, `404` when the stock is not on the watchlist), `DELETE` takes it out (it stays on the watchlist), `PUT /v1/portfolios/{id}/items/order` orders the stocks of a portfolio.
- `GET /v1/portfolios/{id}/deletion-preview` lists the stocks that only this portfolio holds and a `removalToken` of exactly those; `DELETE /v1/portfolios/{id}?confirm=true&removalToken=...` deletes the portfolio and those stocks leave the watchlist. Without `confirm=true`, or with it and no token, the answer is `409` when stocks would leave and nothing changes; the `409` itself carries `stocksToRemove` and the `removalToken` that confirms them, so the preview request is optional. A token of a different set (a stock was put in the portfolio since) is a `409` with the current list and token, and nothing is deleted; a token that is not sixteen hex digits is a `400` (ADR-0049).
- `GET /v1/portfolios/{id}/metrics` (ETag, ADR-0035): per window (`1D` … `5Y`) the `count` of stocks with a number, their equal-weighted `average` and `median`, and the `best` and `worst` stock; plus `stockCount`, `priceStatuses` (`current`, `stale`, `pending`, `unavailable`, `delisted`) and `staleSince`. A stock without a number for a window is left out, not counted as zero; with none the figures are `null`. Decimals are strings. Informational only.
- `GET /v1/watchlist?portfolio={id}` lists only the stocks of that portfolio, combined with the other filters; an unknown or foreign portfolio is `404`.

## Price history and sparklines (milestone 2.7g, ADR-0038)
- `GET /v1/stocks/{market}/{ticker}/prices?range=&interval=` (ETag): the stored days of a catalog stock, oldest first, each with `close` (as traded) and `adjustedClose` (draw this one) as strings and `isFinal`. `range` is `1W`, `1M`, `3M`, `6M`, `YTD`, `1Y` (default), `5Y` or `MAX`, and starts where the performance window of the same name does; `interval` is `day`, `week` or `month` (shown by the last trading day) or `auto` (days up to a year, weeks for `5Y`, months for `MAX`). The answer also has `from`, `to`, `count`, `priceStatus` (`current`, `stale`, `pending`, `unavailable`, or `delisted` with `delistedAt` when the stock no longer trades) and `staleSince`. A stock with no price yet is an empty series (`200`); an unknown stock is `404`; a bad range or interval is `400`.
- `GET /v1/watchlist/sparklines?days=&portfolio=` (ETag): for every stock on the caller's watchlist (or of one portfolio) the adjusted closes of its last `days` stored trading days (5 to 250, default 30), oldest first; ordered by ticker; an empty line for a stock with no price yet. A portfolio that is not the caller's is `404`.

## Delisted stocks and ticker changes (milestone 2.7h, ADR-0039)
- A stock that stopped trading has `priceStatus` `delisted` and a `delistedAt` in the watchlist, in the price series and in the portfolio metrics (`priceStatuses.delisted`); its last price and its history are kept and it never goes stale. `GET /v1/watchlist?priceStatus=delisted` lists them.
- A stock that changed its ticker keeps its id: the watchlist and the series show the new ticker, and a route with the old ticker (`/v1/stocks/{market}/{ticker}/prices`, `PUT /v1/watchlist/items/{market}/{ticker}`, the calculator) still finds the stock. The change is made by the operator (`docs/runbooks/listing-lifecycle.md`), not by the API.

## Calculator (milestone 2.7, ADR-0036 and ADR-0037)
- `POST /v1/calculations/partial-purchase` (no `Idempotency-Key`: a pure computation that stores nothing). The body gives a stock of the catalog (`market` and `ticker`; its newest close, as traded, is the price, and a stale one is used and flagged) **or** a `price` with its `currency`, and exactly one of `amount` (money to invest, in the currency of the price) or `shares` (up to six decimals). An optional `feePercent` (0 to 10, default 0) is the broker's commission as a percentage of the value of the shares: with `amount` it is the total paid and the commission comes out of it; with `shares` the commission is added to their cost. Every decimal is a string.
- The answer carries `mode`, `priceSource` (`catalog` or `manual`), `quoteCurrency`, `priceNative`, `sharesFraction` (cut at six decimals, never rounded up), `amountNative`, `costOneShareGtq` and `amountGtq` (the total paid, commission included, with `feePercent`, `feeNative` and `feeGtq` apart; money rounded to the minor units of its currency, half to even), and the exchange rate used: `fxPath` (for example `["CAD","USD","GTQ"]`), `fxRate` (exact), `fxAsOf`, `fxSource`, `fxStale` and `fxLegs` (each step with its day, source and whether it was inverted), plus `disclaimerKey`: the rate is a reference and a broker's rate, fees and minimum order sizes differ.
- Errors: `400` for a request that is not exactly one source and one mode, a bad number or a quantity out of range; `404` for a stock the catalog does not have (it is never registered from here) or a currency with no rate stored; `422` (`calculator.price_unavailable`) for a stock with no price yet.

## Idempotency in code (ADR-0017, ADR-0022)
A command that creates or triggers work implements `IIdempotentRequest`; its endpoint builds the key with `IdempotencyKeyReader.Require(httpContext)`, which returns `400` with `idempotency.key_required` or `idempotency.key_invalid` when the header is missing or not 16-64 characters of letters, digits, `-` or `_`. The key is scoped by user, HTTP method and route template, and recorded in the same transaction as the effect. A repeated key with the same request replays the first successful result with `Idempotent-Replayed: true` and does not run the handler again; a different request under the same key returns `422` (`idempotency.key_reuse`); a duplicate that arrives while the first is still running waits for it and, if it cannot get the lock in time, returns `409` (`idempotency.in_progress`) with `Retry-After: 1`. Only successes are stored: a failure rolls back and leaves no key, so the client may retry. A first response larger than 64 KB is not stored and its replay returns `409` (`idempotency.replay_unavailable`); fetch the resource with `GET`.
