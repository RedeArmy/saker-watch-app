# ADR-0048: Warming the performance windows, and counting the API processes

- **Status:** proposed
- **Date:** 2026-10-22
- **Deciders:** Eder

## Context
Three things were left open by ADR-0041, ADR-0043 and ADR-0047, and each was a limit that the review of Phase 2 named:
- **Rules the fingerprint cannot see.** ADR-0047 puts a fingerprint of what the calculator does in the key of the performance cache. The numbers also depend on the statements that read the newest close and the close on or before each window's start, which are not in the calculator.
- **The first read after a load.** The stamp of a listing changes with every nightly load, so the first user to read each listing after it pays for computing its windows (about 0.3 to 0.5 s for 500 listings, ADR-0030). It is the same cost every day, and nobody is waiting for the worker.
- **The number of API processes.** The registration cap while Redis is down (ADR-0047) was divided by a setting under `MarketData:Lookup`, and the rate limiters stay in memory because there is one API instance (ADR-0021, which says to revisit it if the API is ever scaled out). Both depend on one fact about the deployment, which belonged in one place.

## Options considered
- **Rules outside the calculator:** raise a number by hand when they change (a memory test again), pin the text of the statements in a test, or hash the statements into the key. A hash of the text of the two statements changes exactly when they do and needs no one; it can be wrong only by not seeing a change that is not in the text (the indexes, the data), which does not change a number.
- **Warming:** compute the windows of every listing from a job after each nightly run, warm each listing from its own load, or leave it. A job per market has no way to know when every listing of the market has loaded. One small job per listing, queued by the load that made the stamp, reads through the same cached reader a user uses, so nothing can be kept that a user would not have computed, and it needs no knowledge of the stamp's precision.
- **The number of processes:** keep two settings, one in each place, or one under `Deployment`. For the limiters: keep them in memory and say so, count in Redis always (a round trip in every request for a single instance), or choose from the number of processes with a fall back to the process when Redis cannot be reached.

## Decision
- **The key tag has a third part.** `RedisPerformanceCache.KeyTag` is `c{version}.{rules}.{queries}`: the manual version, the fingerprint of the calculator (`PerformanceRules`) and the first eight hex digits of the hash of the text of the two statements of `PerformanceReader`. `PerformanceCalculator.Version` stays for emptying the cache on purpose or for a rule none of the fingerprints reach. Event 2803 logs the tag once per process.
- **Loads queue the warming of their slice.** `RefreshStockHandler` and `BackfillStockHandler` queue `WarmPerformanceJob` after they record the success, unless `MarketData:Cache:Enabled` or `MarketData:Cache:WarmAfterLoad` is off. The job is for a market and a slice of `MarketData:Cache:WarmBucketMinutes` (15) minutes counted from the Unix epoch, keyed `marketdata.warm-performance:{market}:{slice}`: the loads of a market in the same slice share it, and it becomes due a minute after the slice ends, when they have committed. The handler reads the listings that loaded in the slice (`IIngestionStamps.LoadedBetweenAsync`) through the cached reader in one batch. A night of loads is a few jobs for a market and not one for each listing; the reads count as misses in `sakerwatch_marketdata_perf_cache_total` and are counted apart in `sakerwatch_marketdata_perf_warm_total`. `scripts/run-k6.sh` measures the first read after a load with and without the job.
- **`Deployment:ApiReplicas` says how many API processes there are** (1 by default, at most 64, validated at startup) and replaces `MarketData:Lookup:ApiReplicas`.
- **The processes count each other.** Each API process writes itself into a sorted set in Redis every 10 seconds with a lease of 30 (`ApiInstanceRegistry`, on the clock of Redis, removed on a graceful stop). `IApiInstances.Count` is the larger of the declared number and the number seen, so an operator who scales out and forgets the setting is still counted with: the limiters move to Redis, the shares of per-process counts shrink, and a warning (event 9110) says that `Deployment:ApiReplicas` is wrong. The count never drops below what is declared; if Redis cannot be reached the last count is kept (event 9112). The worker and tools count what is declared. `sakerwatch_deployment_api_instances{kind}` shows declared, observed and counted.
- **The rate limiters count in Redis when there is more than one process.** `RateLimiting:Backend` is `Auto` (Redis when `IApiInstances.Count` is more than one, memory otherwise), `Memory` or `Redis`; the place is asked for each request. `CallerRateLimiter` is a sliding window counter: the permits of the current window plus those of the one before it weighted by how much of it still overlaps the last window must leave room. A burst at the end of a window followed by another at the start of the next no longer gets twice the limit, and only the requests let through are counted. In Redis the count of a caller is two keys by window number, hashed so that they hold neither the user nor the address, set by one script that reads the clock of Redis. If Redis cannot be reached the request is counted in the memory of the process with the same limit (`sakerwatch_http_rate_limiter_fallback_total`); the limiter never turns off.
- **Asking without taking never waits.** The framework's fixed window limiter, asked for zero permits on a full window, waits for the next window instead of answering no (found when the pre-authentication limiter hung a test). `CallerRateLimiter` answers `AcquireAsync(0)` at once, yes while one more permit would fit and no otherwise, in memory and in Redis, so the pre-authentication limiter asks the same way whatever the backend, and a test pins that it answers within seconds.

## Consequences
- ADR-0021's "the rate limiter stays in memory" is superseded by this for the case it names: scaling the API out needs no change of code, and forgetting to say so is noticed and corrected. With one process nothing changes and no request goes to Redis for a limit (the registry writes one small script every 10 seconds).
- The window of a caller is a sliding one and its `Retry-After` is the time to the end of the current window, a hint that can be a little long or short.
- While Redis is down each process allows the whole limit to a caller (the cost of a fall back that stays on); the metric says it is happening. A process that has just started has not been seen yet for up to 10 seconds.
- The worker does a few small jobs for each market a night. Each one is a cached read of the listings of a slice. A deploy that changes the rules empties nothing: the first reads of the day are the ones the jobs have just made.
- The fingerprint of the statements is of their text, so a change that is only formatting (spaces) changes the keys once.
- A load after the job ran for its slice (a straggler that committed late) is not warmed; its first reader computes it, as before.
